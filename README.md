# Flare Private Perps

**Private, unlinkable perpetuals trading on Flare, enforced by a TEE.**

A Flare Confidential Compute (FCC) extension that lets a user on Flare own and
operate a Hyperliquid (spot + perps) trading account by sending plain on-chain
instructions - **without ever holding the account's private key, and without
anyone being able to link their Flare wallet to their trading account.** The key
is created and used inside a Trusted Execution Environment; the executing code is
attested and registered on-chain, so anyone can verify the thing holding the funds
is exactly the reviewed code.

This is the upstream Flare "Hyperliquid Controlled Accounts" extension, upgraded
with **private deposits and withdrawals**: funding moves in both directions through
pooled, randomized, batched, fixed-denomination transfers, so an observer cannot
correlate your on-chain deposit/withdraw with the Hyperliquid account that gets
funded or unwound.

> **What "private" means (read this):** Hyperliquid is a public ledger, so we
> cannot hide *what* an account does - only *that it is yours*. The guarantee is
> **unlinkability**, and its strength is the batch size. See
> [docs/privacy.md](docs/privacy.md) for the full, honest threat model.

## How it works, in one picture

```
User (Flare wallet)                         Trusted Execution Environment
  |                                            - derives your HL account (seed, in-TEE)
  |  on-chain DEPOSIT (escrow to Vault)        - deposit pool: funds it after a
  |------------------------------------------>    randomized, batched delay
  |                                            - trades it on Hyperliquid
  |  on-chain WITHDRAW (debit)                 - withdraw pool: unwinds it to the
  |------------------------------------------>    treasury after a randomized delay
  |  <--- release from Vault --------------------
```

- **Deposit/withdraw** are on-chain instructions (escrow + release through a shared
  `Vault`); the *private* funding/reclaim happens inside the TEE, off-chain and
  delayed, so it can't be time/amount-correlated.
- **Trades** (long/short, leverage, cancel) are on-chain instructions relayed to the
  TEE, which signs and executes them on Hyperliquid.

## Deploying: the one gotcha ("Extension ID is not set.")

A deposit/trade that reverts on-chain with **`Extension ID is not set.`** means the
deployed `HyperliquidInstructionSender` was never wired to its extension - the
registration step (`setExtensionId`, and `setVault` for deposits) did not run. Fix
it by completing the full deploy, which runs deploy -> register -> `setExtensionId`:

```bash
./scripts/full-setup.sh --chain coston2
```

Then seed the treasury (below) or funding has nothing to send. Until the stack is
fully registered, the on-chain path reverts by design.

### TEE governance

Every TEE machine registers under a **governance** — a set of signer addresses
and a threshold that authorize governance actions for the extension (e.g.
machine-path-list updates). Two parties must agree on this set, or `register-tee`
reverts with `InvalidGovernanceHash`:

- the **TEE node**, which signs its machine data with a `governanceHash` derived
  from `(signers, threshold)`, and
- the **on-chain registry**, where the governance is registered.

The scaffold keeps them consistent by reading both from one place — your `.env`:

```bash
GOVERNANCE_SIGNERS="0xAbc...,0xDef..."   # comma-separated 0x addresses
GOVERNANCE_THRESHOLD=2
```

If unset, both default to **the deployer (`INITIAL_OWNER`) as the sole signer,
threshold 1** — fine for development. During `post-build`, the `set-governance`
step registers the set on-chain (idempotently) before `register-tee`, and the
same values are passed to the node container via Docker Compose.

## Creating Your Extension

The scaffold ships with placeholder code marked with `TODO` comments. To build your extension, you modify 5 files:

| # | File | What you do |
|---|------|-------------|
| 1 | `internal/config/config.go` | Define your OPType and OPCommand constants (e.g. `OPTypeGreeting = "GREETING"`, `OPCommandSayHello = "SAY_HELLO"`) |
| 2 | `pkg/types/types.go` | Define your request, response, and state structs |
| 3 | `internal/extension/extension.go` | Add routing cases and implement your action handlers |
| 4 | `pkg/types/register.go` | Register decoders for your request/response types ([details](docs/types-server.md#adding-your-own-types)) |
| 5 | `contracts/InstructionSender.sol` | Add matching `bytes32` constants and send functions |
| 6 | `tools/cmd/run-test/main.go` | Write test payloads and response assertions |

The key link between your Solidity contract and Go code is the **OPType** and **OPCommand** pair — both must match across all three layers:

```
Solidity:  bytes32 constant OP_TYPE_GREETING     = bytes32("GREETING");
           bytes32 constant OP_COMMAND_SAY_HELLO  = bytes32("SAY_HELLO");
           bytes32 constant OP_COMMAND_SAY_GOODBYE = bytes32("SAY_GOODBYE");

Go config: OPTypeGreeting      = "GREETING"
           OPCommandSayHello   = "SAY_HELLO"
           OPCommandSayGoodbye = "SAY_GOODBYE"

Go router: case dataFixed.OPType == teeutils.ToHash(config.OPTypeGreeting):
               // sub-route on OPCommand
               case dataFixed.OPCommand == teeutils.ToHash(config.OPCommandSayHello):
               case dataFixed.OPCommand == teeutils.ToHash(config.OPCommandSayGoodbye):
```

Register.go maps each `(OPType, OPCommand)` pair to its decoder. The decoder registry no longer requires a `Kind()` method; `NewJSONDecoder[T]()` takes no arguments, and `NewABIDecoder[T](abi)` takes only the ABI string.

Each action handler follows a 4-step pattern: decode the request, validate it, execute your logic, and return a result via `buildResult()`.

## Quick Start

With local infrastructure running (`docker compose up` from `e2e/`), run everything in one shot:

```bash
./scripts/full-setup.sh --test
```

This runs the full lifecycle:
1. **Pre-build** — compile contracts, deploy, register extension, write `config/extension.env`
2. **Docker Compose** — start redis, proxy, and extension TEE as containers
3. **Post-build** — register TEE version and TEE machine on-chain
4. **Test** — send instructions and verify results

### Step-by-step

If you prefer running each phase individually:

#### 1. Pre-build

```bash
./scripts/pre-build.sh
```

Deploys your contract, registers the extension, and writes `config/extension.env` with `EXTENSION_ID` and `INSTRUCTION_SENDER`.

To override defaults:
```bash
ADDRESSES_FILE=/path/to/deployed-addresses.json CHAIN_URL=http://your-node:8545 ./scripts/pre-build.sh
```

#### 2. Start services (Docker Compose)

```bash
docker compose up -d --build
```

`docker compose up --build` automatically builds the **extension-tee** image from your extension source code (via the `Dockerfile` and `build:` block in `docker-compose.yaml`). This is the image you rebuild whenever you change your extension code. The `--build` flag ensures it picks up your latest changes; you can omit it on subsequent runs if you haven't changed any code.

This starts three containers:
- **redis** — queue storage for the proxy
- **ext-proxy** — TEE proxy (pre-built image) using `config/proxy/extension_proxy.docker.toml`
- **extension-tee** — your extension: tee-node + extension server built from source

The compose file reads `EXTENSION_ID` from `config/extension.env` (written by pre-build). It joins the infrastructure network (`docker_default`) so the proxy can reach `indexer-db` and `node`.

Check status or stop:
```bash
docker compose ps
docker compose logs -f extension-tee
docker compose down
```

#### 3. Post-build

```bash
./scripts/post-build.sh
```

Waits for the proxy to be ready, then registers the TEE version and TEE machine on-chain.

#### 4. Test

```bash
./scripts/test.sh
```

## Deploying to Coston2

Coston2 is Flare's public testnet. Unlike local dev (which runs against a Hardhat node with pre-deployed contracts), Coston2 deployment connects to the live testnet RPC, uses real signing policies, and requires a publicly accessible proxy URL.

### Prerequisites

- A **funded Coston2 account** — you need a private key with testnet C2FLR for gas. Get testnet tokens from the [Coston2 faucet](https://faucet.flare.network/coston2).
- **ngrok** (or similar tunneling tool) — the TEE proxy must be publicly reachable so data providers can deliver cosigned responses. Install from [ngrok.com](https://ngrok.com).
- **Indexer DB credentials** — the proxy needs access to a Flare indexer database to fetch signing policies. Ask the Flare team for credentials, or use the values in the example config.

### 1. Configure `.env`

Copy `.env.example` and fill in your values:

```bash
cp .env.example .env
```

Key values to set:

| Variable | Value | Notes |
|----------|-------|-------|
| `DEPLOYMENT_PRIVATE_KEY` | Your funded Coston2 private key | Used for contract deployments and on-chain calls |
| `INITIAL_OWNER` | Address derived from `DEPLOYMENT_PRIVATE_KEY` | Owner of deployed contracts |
| `PROXY_PRIVATE_KEY` | Same or different funded key | Used by the proxy for signing |
| `CHAIN_URL` | `https://coston2-api.flare.network/ext/C/rpc` | Coston2 RPC endpoint |
| `ADDRESSES_FILE` | `./config/coston2/deployed-addresses.json` | Pre-populated with Coston2 contract addresses |
| `LOCAL_MODE` | `false` | **Must be `false`** on live networks (enables attestation) |
| `NORMAL_PROXY_URL` | `https://tee-proxy-coston2-1.flare.rocks` | Flare's Coston2 normal/FTDC proxy |
| `EXT_PROXY_URL` | `https://<your-subdomain>.ngrok-free.dev` | Your ngrok tunnel URL (see step 3) |

### 2. Configure the proxy

The proxy config files live in `config/proxy/`. For Coston2, there are two files:

- **`extension_proxy.coston2.docker.toml`** — used inside Docker (references `redis` service name)
- **`extension_proxy.coston2.toml`** — used when running the proxy outside Docker

Copy from the example files if starting fresh:

```bash
cp config/proxy/extension_proxy.coston2.docker.toml.example config/proxy/extension_proxy.coston2.docker.toml
cp config/proxy/extension_proxy.coston2.toml.example config/proxy/extension_proxy.coston2.toml
```

Then fill in the `[db]` section with your indexer database credentials:

```toml
[db]
host = "<indexer-db-host>"
port = 3306
database = "<indexer-db-name>"
username = "<indexer-db-user>"
password = "<indexer-db-password>"
log_queries = false
```

The Coston2 contract addresses (`flare_systems_manager`, `relay`, `voter_registry`) are already set correctly in the example files. The `chain_id` is `114` (Coston2).

### 3. Start ngrok

The extension proxy must be publicly accessible so that data providers can reach it. Start an ngrok tunnel pointing to the proxy's external port (6674):

```bash
ngrok http 6674
```

Copy the generated HTTPS URL (e.g., `https://abc123.ngrok-free.dev`) and set it as `EXT_PROXY_URL` in your `.env`.

### 4. Pre-build (deploy & register)

```bash
./scripts/pre-build.sh
```

This deploys your `InstructionSender` contract to Coston2 and registers your extension on the `TeeExtensionRegistry`. The scripts auto-detect Coston2 addresses when `LOCAL_MODE=false`.

### 5. Start services (Docker Compose)

On Coston2, use the override file that swaps in the Coston2 proxy config and chain URL:

```bash
docker compose -f docker-compose.yaml -f docker-compose.coston2.yaml up -d --build
```

This does the same as the local `docker compose up` but:
- Mounts `config/proxy/extension_proxy.coston2.docker.toml` instead of the local proxy config
- Sets `CHAIN_URL` to the Coston2 RPC endpoint
- Creates its own network (`extension-scaffold-coston2`) instead of joining the local e2e `docker_default` network

Check status:
```bash
docker compose -f docker-compose.yaml -f docker-compose.coston2.yaml ps
docker compose -f docker-compose.yaml -f docker-compose.coston2.yaml logs -f extension-tee
```

### 6. Post-build (register TEE)

```bash
./scripts/post-build.sh
```

This allows the TEE version, registers the extension's TEE **governance** (see [TEE governance](#tee-governance)), and registers the TEE machine on-chain. It reads `EXT_PROXY_URL` and `NORMAL_PROXY_URL` from your `.env`, so make sure ngrok is running and the URL is correct.

### 7. Test

```bash
./scripts/test.sh
```

Sends instructions on-chain via your deployed `InstructionSender` and polls the proxy for results.

### Stopping Coston2 services

```bash
docker compose -f docker-compose.yaml -f docker-compose.coston2.yaml down
```

## Hyperliquid Controlled Accounts

This repository implements a Flare Compute Extension that lets users trade on Hyperliquid (spot + perps) by sending plain on-chain instructions on Flare. The TEE holds a dedicated Hyperliquid account per user, executes their actions on Hyperliquid's testnet, and the user never bridges funds off Flare.

For the full on-chain e2e runbook on Coston2 (deploy → register → drive deposit/trade/withdraw from on-chain transactions → verify on Hyperliquid), see [docs/hyperliquid.md](docs/hyperliquid.md#11-on-chain-e2e-on-coston2).

### Seeding the treasury (testnet setup)

The extension uses a single treasury HL account that is funded once from the Hyperliquid testnet faucet. On a `DEPOSIT` instruction the TEE transfers mock USDC from the treasury to the user's derived HL account.

To seed the treasury:

1. Generate a dedicated keypair for `HL_TREASURY_KEY` (or use an existing funded one).
2. Visit [app.hyperliquid-testnet.xyz/drip](https://app.hyperliquid-testnet.xyz/drip) and claim the faucet for that address. The faucet provides **1,000 mock USDC**, one-time per address.
3. Note: faucet use requires a **$5 mainnet activation** of the address on Hyperliquid mainnet. This is a one-time Hyperliquid requirement, not a Flare requirement.
4. Set `HL_TREASURY_KEY` in your `.env` to the private key (hex) of that funded address.

### Account modes: unified vs. standard (important)

Hyperliquid accounts have an **abstraction mode** (`unifiedAccount`, `portfolioMargin`, or `disabled`/standard). **Unified accounts disable inter-account transfers** (`usdSend`/`spotSend`) — HL rejects them with `"Action disabled when unified account is active"`. Because the funding model moves USDC between the treasury and per-user accounts, those accounts must be in **standard mode**.

The extension handles this automatically:

- On startup it best-effort sets the **treasury** to standard mode via the `userSetAbstraction` action (`abstraction: "disabled"`). This is rejected if the treasury has **open positions/orders**, so keep the treasury flat — it is a funding account, not a trading account.
- Fresh derived user accounts come up in `default` mode, which already permits transfers and spot↔perp class transfers, so they need no change.

Mechanics, for reference:

- **Funding** uses `spotSend` (the USDC token transfer), which credits the recipient's **spot** balance.
- Since spot and perp balances are separate in standard mode, the order handler **sweeps collateral to the side each order needs**: `spot→perp` before a perp order, `perp→spot` before a spot buy (via `usdClassTransfer`).
- You can inspect an account's mode with the info query `{"type":"userAbstraction","user":"0x..."}`.

### Environment variables

Copy `.env.example` and fill in the Hyperliquid-specific values:

| Variable | Default | Description |
|---|---|---|
| `HYPERLIQUID_URL` | `https://api.hyperliquid-testnet.xyz` | Hyperliquid API endpoint; signing domain is determined by this URL |
| `HL_MASTER_SEED` | (required, no default) | 32+ byte hex seed used to derive per-user HL keys — **KEEP SECRET** |
| `HL_TREASURY_KEY` | (required, no default) | Private key (hex) of the faucet-funded treasury HL account — **KEEP SECRET** |
| `HL_MAX_DEPOSIT_USD` | `1000` | Maximum USD amount for a single `DEPOSIT` instruction (guardrail) |
| `HL_MAX_TOTAL_DEPOSIT_USD` | `5000` | Enforced against the current net ledger total; ultimately bounded by the treasury balance (global cap) |

> Both `HL_MASTER_SEED` and `HL_TREASURY_KEY` are secrets. Never commit real values. Leave them empty in `.env.example`.

### Private deposit & withdraw (the Private Perps upgrade)

Off by default (original synchronous behaviour). Turn on unlinkable funding in both
directions with `HL_PRIVATE_DEPOSIT=true`. Full rationale + threat model in
[docs/privacy.md](docs/privacy.md).

| Variable | Default | Description |
|---|---|---|
| `HL_PRIVATE_DEPOSIT` | `false` | Enable delayed/batched private deposit **and** withdraw |
| `HL_DENOMINATIONS` | `25,100,500` | Allowed fixed deposit/withdraw amounts (USD) |
| `HL_BATCH_MIN` | `1` | Min matured entries funded/settled together (the anonymity set) |
| `HL_FUND_DELAY_MIN_SECONDS` | `20` | Randomized funding/payout delay, lower bound |
| `HL_FUND_DELAY_MAX_SECONDS` | `60` | Randomized delay, upper bound |
| `HL_FUND_TICK_SECONDS` | `5` | How often the batchers drain due entries |

Demo defaults are short so the flow is visible. For real unlinkability use a large
batch and a long window (e.g. `HL_BATCH_MIN=10`, delay 30 min - 6 h) - privacy
strength is the batch size.

### Instruction set

The extension uses OPType `HL`, sub-routed by OPCommand. Send instructions via `HyperliquidInstructionSender.sol` on Flare / Coston2.

| OPCommand | Contract function | JSON payload (after `msg.sender`) | TEE action |
|---|---|---|---|
| `DEPOSIT` | `deposit(uint256 usdAmount)` | `{"usdAmount": N}` | Treasury → user `UsdTransfer`; ledger credit |
| `PLACE_ORDER` | `placeOrder(bytes)` | `{"market": "spot"\|"perp", "coin": "ETH", "isBuy": true, "orderType": "market"\|"limit", "size": N, "limitPx": N, "reduceOnly": false, "leverage": N, "isCross": true}` — `limitPx`, `reduceOnly`, `leverage`, `isCross` are optional | Set leverage if perp; class-transfer USDC spot↔perp as needed; `MarketOpen` / `Order` |
| `CANCEL` | `cancel(bytes)` | `{"coin": "ETH", "orderId": N}` | `BulkCancel` on HL |
| `WITHDRAW` | `withdraw(uint256 usdAmount)` | `{"usdAmount": N}` | User → treasury `UsdTransfer`; ledger debit (**stub in v1 — no FXRP back to Flare yet**) |

#### PLACE_ORDER payload fields

| Field | Required | Values |
|---|---|---|
| `market` | yes | `"spot"` or `"perp"` |
| `coin` | yes | e.g. `"ETH"`, `"BTC"` |
| `isBuy` | yes | `true` / `false` |
| `orderType` | yes | `"market"` or `"limit"` |
| `size` | yes | quantity (float) |
| `limitPx` | no | limit price; required when `orderType = "limit"` |
| `reduceOnly` | no | `true` to reduce position only (default `false`) |
| `leverage` | no | integer leverage; only applied for perp orders |
| `isCross` | no | `true` = cross margin, `false` = isolated (default `true`) |

### Read path

The extension exposes two complementary ways to read account state:

- **Authoritative (TEE `/state`):** the TEE publishes per-user state including the derived `hlAddress`, the internal balance (`balanceUsd`), and cached positions. Clients poll this via the proxy state endpoint.
- **Live (frontend direct):** once a client has the user's `hlAddress` (from `/state`), it can read positions, fills, and order book data straight from Hyperliquid's public info API (`https://api.hyperliquid-testnet.xyz/info`) for real-time UX without routing through the TEE.

### v1 deferrals

The following items are **out of scope for v1** and deferred to later milestones:

- **Flare Smart Accounts (FSA):** v1 identifies users by the EOA that calls the on-chain contract. FSA support is a future milestone.
- **Real FXRP escrow / withdrawal:** `DEPOSIT` is a mock funded by the testnet treasury; `WITHDRAW` debits the ledger but does not yet move real FXRP back to Flare. Full escrow + FXRP→FUSD conversion is deferred.
- **Multi-machine key consistency:** each TEE machine derives a different HL account for the same user. v1 runs a single TEE machine. Multi-machine needs either sticky per-user routing or shared key custody via PMW — deferred and flagged in the design spec.

For full design rationale, risks, and open questions see the design spec: [`docs/superpowers/specs/2026-06-30-hyperliquid-controlled-accounts-design.md`](docs/superpowers/specs/2026-06-30-hyperliquid-controlled-accounts-design.md).
